Understanding MCP Architecture: How AI Assistants, LLMs, MCP Clients, and MCP Servers Work Together

A practical, beginner-friendly guide to understanding how Model Context Protocol connects AI models with external tools, APIs, databases, and applications.

Technical Guide · 12–15 min read

Introduction: Understanding the Missing Connection

Model Context Protocol (MCP) is becoming an important part of the modern AI ecosystem. It provides a standardized way for AI applications to connect with external systems and use their capabilities.

You might already understand what an AI assistant is, what an LLM does, how APIs work, and why external tools are useful. However, understanding how all these components communicate with one another is where things can become confusing.

MCP architecture introduces four important components:

01

AI Assistant

The application through which users interact with AI.

02

LLM

The reasoning and language-generation engine.

03

MCP Client

Communicates with MCP servers and executes tool requests.

04

MCP Server

Exposes tools and capabilities to AI applications.

Let's understand how these four components work together using a real-world example.

1. Understanding the Four Components

1. AI Assistant or Chatbot

The AI assistant is the application that users interact with. Examples include ChatGPT, Claude, and other AI-powered applications.

It receives user questions, manages conversation context, communicates with the LLM, and coordinates tool execution. In MCP terminology, this application is called the MCP Host.

2. Large Language Model (LLM)

The LLM is the intelligence behind the assistant. It understands natural language, interprets user intent, determines whether external information is required, and selects appropriate tools when they are available.

An important distinction: the LLM does not normally communicate directly with an MCP server. The host application coordinates communication between them.

3. MCP Client

The MCP client is the communication layer between the host application and an MCP server.

It establishes a connection, discovers available tools, sends tool requests, and receives results.

Typically, an MCP host creates a separate client connection for each MCP server.

4. MCP Server

An MCP server is a program that exposes capabilities through the MCP protocol. These capabilities can include tools, resources, and prompts.

An MCP server might connect to a weather API, a stock market API, a database, a local filesystem, or another application.

Important: An MCP server does not necessarily contain the actual data. It can act as an adapter that retrieves information from an external API or system.

2. How Are These Four Components Connected?

The AI assistant acts as the host and coordinates the entire process. The LLM makes decisions, while MCP clients communicate with their respective servers.

AI ASSISTANT / MCP HOST Chat interface and application logic
↓
LLM Understands requests and selects tools
↕
MCP CLIENTS Connect to MCP servers and route tool calls
↓
Weather MCP Weather tools
Finance MCP Stock tools
Movies MCP Movie tools
↓
EXTERNAL SYSTEMS APIs · Databases · Local Files · Applications

The LLM and MCP clients are coordinated by the host application. The diagram is conceptual: actual implementations may have multiple clients and additional orchestration logic.

3. Let's Follow a Real Question: What Is the Temperature in Lucknow?

Imagine asking an AI assistant:

What is the current temperature in Lucknow?

Assume that the application has a Weather MCP server connected to a weather API.

Step 1: The User Asks a Question

The chatbot receives the question and sends the user's message, along with relevant conversation context, to the LLM. 

What is the current temperature in Lucknow?

At this point, the weather API has not necessarily been called.

Step 2: The LLM Identifies the Required Tool

The LLM has access to descriptions of the available tools. For example, the Weather MCP server exposes the following tool: 

{
  "name": "get_weather",
  "description": "Get current weather for a city",
  "inputSchema": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string"
      }
    },
    "required": ["city"]
  }
}

The LLM understands that current weather information requires an external data source.

It selects the get_weather tool and prepares the required argument. 

{
  "tool": "get_weather",
  "arguments": {
    "city": "Lucknow"
  }
}

This is a tool-call decision, not the actual weather result. The LLM has decided what needs to happen, but it has not retrieved the temperature itself.

Step 3: The Host Routes the Tool Request

The host application receives the LLM's tool-call decision. It identifies which MCP client is connected to the server that provides get_weather.

The MCP client then sends an MCP request to the Weather MCP server. 

{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "city": "Lucknow"
    }
  }
}

This is a JSON-RPC message following the MCP protocol.

Step 4: The MCP Server Executes the Tool

The Weather MCP server receives the request and executes the corresponding function.

Internally, its implementation might look like this: 

def get_weather(city):

    response = requests.get(
        "https://weather-api.example.com/current",
        params={"city": city}
    )

    return response.json()

The server calls the external weather API, which might return the following response: 

{
  "city": "Lucknow",
  "temperature": 29,
  "condition": "Cloudy",
  "humidity": 65
}

The MCP server converts the result into an MCP tool response and sends it back to the MCP client.

Step 5: The Result Returns to the LLM

The result travels back through the same connection:

Weather API
↓
Weather MCP Server
↓
MCP Client
↓
AI Assistant / Host
↓
LLM

The host provides the tool result to the LLM as additional conversation context.

The LLM now has access to the actual weather information and can generate a meaningful response.

Step 6: The AI Assistant Displays the Final Answer

The LLM generates a natural-language response:

The current temperature in Lucknow is 29°C, with cloudy conditions and 65% humidity.

The chatbot displays this answer to the user.

4. How Does the AI Decide Which MCP Server to Call?

This is one of the most important concepts in MCP architecture.

Imagine that an AI application has connected five MCP servers:

MCP Server Available Tools
Weather get_weather, get_forecast
Finance get_stock_price, get_company_info
Movies search_movies, get_release_date
Filesystem read_file, list_directory
Database execute_sql, get_schema

Who decides that a weather question should go to the Weather MCP server instead of the Finance MCP server?

Typically, the LLM selects the appropriate tool, while the host application handles the routing and execution.

Step 1: MCP Clients Discover Available Tools

When an MCP client connects to a server, it can request the list of tools supported by that server using tools/list. 

Weather MCP Client
       |
       | tools/list
       v
Weather MCP Server
       |
       | Returns:
       | get_weather
       | get_forecast
       v
Weather MCP Client

The Finance MCP server might return get_stock_price and get_company_info.

Step 2: The Host Makes Tool Definitions Available to the LLM

The host application collects tool definitions from its connected MCP clients and makes the relevant tools available to the LLM. 

Available tools:

1. get_weather(city)
   Description: Get current weather for a city.

2. get_stock_price(symbol)
   Description: Get the latest stock price.

3. search_movies(query)
   Description: Search for movies.

4. read_file(path)
   Description: Read a local file.

The LLM does not need to know how the internal code of every MCP server works.

It needs to understand the tool descriptions, their input parameters, and what each tool is intended to do.

Step 3: The LLM Selects the Appropriate Tool

Question: What is the temperature in Lucknow?

Selected tool: get_weather(city="Lucknow")

Question: What is the current share price of Infosys?

Selected tool: get_stock_price(symbol="INFY")

Question: Which movies were released this week?

Selected tool: search_movies(query="recent releases")

The LLM uses its language understanding and the available tool descriptions to select the appropriate tool.

Important: The LLM generally performs model-driven tool selection. The MCP protocol itself does not magically understand the user's question and choose a server.

5. How Does the Host Know Which Client to Use?

There is an important distinction between tool selection and tool routing.

The LLM selects the tool. The host application knows which MCP client is connected to the server that provides that tool.

For example, the host might maintain an internal registry: 

tool_registry = {
    "get_weather": weather_client,
    "get_stock_price": finance_client,
    "search_movies": movies_client,
    "read_file": filesystem_client
}

When the LLM selects get_stock_price, the host can route the request as follows: 

client = tool_registry["get_stock_price"]

result = await client.call_tool(
    "get_stock_price",
    {"symbol": "INFY"}
)

The Finance MCP client communicates with its connected Finance MCP server.

This registry is an illustrative implementation. The MCP protocol does not prescribe one specific internal registry design.

6. What Happens When There Are 100 MCP Servers and 1,000 Tools?

A real-world AI application might have access to hundreds of MCP servers and thousands of tools.

Sending every available tool description to the LLM for every request can be inefficient. It increases token usage and consumes context.

There are several ways to manage this situation.

Approach 1: Expose All Available Tools

The application provides all available tool definitions to the LLM. The model selects the appropriate tool.

This is straightforward but can become expensive when the number of tools grows.

Approach 2: Filter Tools Before Sending Them to the LLM

The host application can filter tools using categories, user permissions, application context, or semantic search.

For example, if a user is working inside a database IDE, the host might prioritize database and SQL tools.

Approach 3: Progressive Tool Discovery

Instead of exposing all tools immediately, the application can initially expose a smaller discovery tool.

For example: 

search_available_tools(query)

The LLM might request: 

{
  "query": "Find the current stock price of Infosys"
}

The application searches its tool registry and discovers a suitable tool: 

get_stock_price(symbol)

It can then make that tool available to the LLM for execution.

Progressive tool discovery helps applications manage large tool collections without overwhelming the model with every tool definition at once.

7. Does an MCP Server Always Need an API?

No. An MCP server is an adapter between an AI application and a capability or data source.

MCP SERVER Exposes tools through MCP
↓
REST API
SQL Database
Local Files
Python Functions
Browser Automation
Other Systems

For example:

  • A Weather MCP server can call a weather API.
  • A Database MCP server can execute SQL queries.
  • A Filesystem MCP server can read local files.
  • A custom MCP server can execute Python functions.

The MCP protocol standardizes how the AI application discovers and invokes these capabilities.

8. The Entire MCP Request-Response Cycle

Let's put everything together in one sequence.

1. User asks a question
↓
2. AI Assistant sends context to the LLM
↓
3. LLM selects an appropriate tool
↓
4. Host identifies the relevant MCP client
↓
5. MCP Client sends tools/call
↓
6. MCP Server executes the tool
↓
7. External system returns data
↓
8. Result returns through MCP Client
↓
9. Host sends tool result to the LLM
↓
10. LLM generates the final response
↓
11. AI Assistant displays the answer

9. The Most Important Concepts to Remember

Component Primary Responsibility
AI Assistant / Host Manages conversation and coordinates execution.
LLM Understands intent and selects appropriate tools.
MCP Client Discovers tools and communicates with MCP servers.
MCP Server Exposes and executes capabilities.
External System Provides actual information or performs an operation.
The LLM decides what needs to be done. The MCP client transports the request. The MCP server does the actual work. The LLM interprets the result and explains it to the user.

10. What's the Best Way to Learn MCP Further?

Once you understand the architecture, the next logical step is to explore it through actual Python code.

A useful learning project is to build a Weather MCP server and connect it to an LLM.

  1. Build a Weather MCP server.
  2. Create a get_weather() tool.
  3. Define the tool's input schema.
  4. Connect the MCP client to the server.
  5. Execute tools/list to discover available tools.
  6. Pass the tool definitions to an LLM.
  7. Execute the tool call selected by the LLM.
  8. Send the result back to the LLM.
  9. Generate the final response.

Tracing this complete flow in code will help you understand not just what MCP is, but how it actually works internally.
